## 四、本地安装阻塞与撤回

启动原有 Colima `tianxing` 后，现有本地 PostgreSQL 17 容器恢复健康；未修改 Compose、环境文件或密钥。仅对回环地址的 `tianxing` 库、`tianxing_app` 身份执行新脚本空跑。实际数据库为 PostgreSQL 17，身份无超级用户权限；创建新学校表时返回 `42501`，提示组织表访问被拒。随后只读检查确认该身份对 `access_organizations`（组织表）和 `identity_users`（用户表）均无 `REFERENCES`（建立外键引用）权限；事务回滚。收尾只读复核 PostgreSQL 17.10 健康，四张新表全部不存在。

本票禁止修改其他模块及放宽权限，故不对共享表执行授权，不把外键去掉，也不换用常用库管理员身份强行安装。**停止点是本地迁移身份／共享依赖权限的另案处理；不是本票自行放行的权限调整。**本地环境已能运行，但本票需要的实际安装链路不可用，整体仍 blocked。

隔离验证使用已有缓存的 `postgres:17.10-alpine3.24` 镜像，禁止自动拉取，端口只绑定回环，数据在一次性容器内。先按原有冻结基线构建合成库，再由该临时库管理员执行本票 SQL；这不会证明常用库受限身份可以执行。另测受限身份执行空跑同样报 `42501`、回滚且旧引用不变。

撤回分两层：

1. **已实际验证的 SQL 撤回**：在一次性本地 PostgreSQL 17 中执行新增结构、写合成资料、执行向下 SQL、核对旧案件引用摘要不变，再重新执行向上 SQL，确认新学校表为空。撤回只删四张新表及六个配套函数；不使用级联删除，不改旧表。临时合成资料随测试库销毁，不是清除常用库的三所合成学校。
2. **常用库包装脚本的成功撤回未验证**：`scripts/db/school-directory-local.ts` 的 `--rollback` 只允许本地目标；先锁四表，由表所有者在同一事务检查全部为空（检查时临时取消强制 RLS），非空即拒绝且回滚；空才执行向下 SQL。没有授予任何新权限。由于常用库安装已受阻，未在那里运行成功安装或成功撤回，也未在隔离库取得该包装脚本的成功撤回证据，不得把上项 SQL 证据等同于包装脚本验收。

复核使用 Node.js 22 与 pnpm 10.34.4。在另案解决权限前，**不要执行 `--apply` 或直接向下 SQL**。后续获准后可先执行 `node --env-file=.env.migration.local scripts/db/school-directory-local.ts --dry-run`；空跑、安装、撤回仍须逐步按当时授权与实际结果交接。数据进入后，该空库撤回方式不再适用，须另案确定资料与履历保留办法。
